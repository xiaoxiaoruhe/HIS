# 盘点单审批流程接口实现过程（G10）

> 记录「提交审批、审批通过、撤回、驳回」四个接口从需求分析到编码、测试的完整过程，作为后续 G8/G9 实现的方法参考。

## 1. 需求来源

接口文档 `接口文档.md` 中，盘点单相关的功能分组：

| 分组 | 功能 | 状态 |
|------|------|------|
| G8 | 盘点单新增保存：新增单据、保存单据、保存并提交审批 | 待实现 |
| G9 | 盘点单查询提交：获取单据列表、获取单据详情、提交审批 | 部分实现 |
| G10 | 盘点单审批流转：撤回审批、审批通过、驳回审批 | 已实现 |

本文覆盖 G10 的 3 个接口，加上 G9 中的「提交审批」，共 4 个接口。

## 2. 数据模型与状态机

### 2.1 涉及的四张表

| 表 | 作用 |
|----|------|
| `wkf_supply_request` | 供应请求聚合根。**同表多行**：同一 `bus_no` 聚合多行明细，共享审批状态 |
| `wkf_inventory_item` | 库存项。由「物品 + 批号 + 库房」三元组定位唯一库存 |
| `inventory_lock` | 库存锁定。审批期间锁定库存，防止被其它单据并发改动 |
| `doc_inventory_item_snapshot` | 库存明细快照。冻结提交时的账面，作审计依据 |

### 2.2 状态机

```
DRAFT ──提交(submit)──> PENDING_APPROVAL ──通过(approve)──> APPROVED
                            │
                            ├──撤回(withdraw)──> DRAFT
                            └──驳回(reject)──> REJECTED
```

### 2.3 三元组定位库存

`selectAllItemsByBusNo(itemId, lotNumber, locationId)` 用 `item_id + lot_number + location_id` 三条件查库存项，这是所有后续动作（锁、快照、平账）的前提。

## 3. 接口与 DTO/VO 设计

### 3.1 四个接口

| 接口 | 方法/路径 | 入参 | 状态流转 |
|------|-----------|------|----------|
| 提交审批 | PUT `/pharmacy/submit-approval` | OperatorDTO | DRAFT → PENDING_APPROVAL |
| 审批通过 | PUT `/pharmacy/approve-approval` | ApprovalDTO | PENDING_APPROVAL → APPROVED |
| 撤回审批 | PUT `/pharmacy/withdraw-approval` | OperatorDTO | PENDING_APPROVAL → DRAFT |
| 驳回审批 | PUT `/pharmacy/reject-approval` | ApprovalDTO | PENDING_APPROVAL → REJECTED |

### 3.2 DTO / VO

`OperatorDTO`（操作人，提交/撤回用）：

```java
@Data
public class OperatorDTO {
    @NotNull private String busNo;      // 单据号
    @NotNull private String createdBy;  // 操作人（制单人）ID
}
```

`ApprovalDTO`（审批人，通过/驳回用）：

```java
@Data
public class ApprovalDTO {
    @NotNull private String busNo;       // 单据号
    @NotNull private String approverId;  // 审批人ID
    private String remark;               // 备注（驳回原因）
}
```

`InventoryOrderApprovalVO`（统一返回）：`busNo / createdBy / approverId / statusEnum / createdAt / updatedAt / totalPrice` 等。

## 4. 实现步骤

### 4.1 Mapper 层

**WkfSupplyRequestMapper** —— 明细查询 + 状态更新（状态更新都用 `status_enum` 当前值做乐观锁条件）：

```java
List<WkfSupplyRequest> findAllItemsByBusNo(String busNo);  // 按单号查全部明细
int updateStatusToDraft(String statusEnum, String applicantId, LocalDateTime applyTime, String busNo);
int updateStatusToApproved(String statusEnum, String approverId, LocalDateTime approvalTime, String busNo);
int updateStatusToWithdraw(String statusEnum, String busNo);                          // 撤回：清空申请人/时间
int updateStatusToReject(String statusEnum, String approverId, LocalDateTime approvalTime, String reason, String busNo);
```

对应的 XML 里，每条 UPDATE 都带 `WHERE bus_no = #{busNo} AND is_deleted = 0 AND status_enum = '...'`，命中 0 行说明状态已被并发改动，用于防重复提交/重复审批。

**InventoryLockMapper**：

```java
List<InventoryLock> findLocksByInventoryId(String inventoryId);  // 查某库存项上生效的锁(lock_flag=1)
int releaseLock(String inventoryId, String busNo);               // 释放锁(lock_flag置0)
```

**WkfInventoryItemMapper**：

```java
WkfInventoryItem selectAllItemsByBusNo(String itemId, String lotNumber, String locationId);  // 三元组定位库存
int updateQuantity(String id, BigDecimal quantity);                                          // 平账：账面=实盘
```

**DocInventoryItemSnapshotMapper**：

```java
int deleteByBusNo(String busNo);  // 撤回时物理删除快照
```

### 4.2 Service 层

#### 4.2.1 submitApproval —— 提交审批

状态流转 `DRAFT → PENDING_APPROVAL`，核心动作：**验锁 → 加锁 → 冻结快照 → 改状态**。

```java
@Transactional(rollbackFor = Exception.class)
public InventoryOrderApprovalVO submitApproval(OperatorDTO operatorDTO) {
    // 1. 判空 busNo
    // 2. findAllItemsByBusNo 查明细，判空
    // 3. 逐行校验 statusEnum == "DRAFT"
    // 3.5 校验无重复明细：HashSet 存 itemId|lotNumber|purposeLocationId 三元组
    // 4. 逐明细：查库存 → 验锁 → 加锁 → 冻结快照
    //    验锁：findLocksByInventoryId 遍历，若是本单据的锁则跳过(幂等)，否则抛"已被单据xx锁定"
    //    加锁：insert InventoryLock(lockFlag=true, status=LOCKED)
    //    快照：insert DocInventoryItemSnapshot(冻结账面 quantity)
    // 5. updateStatusToDraft("PENDING_APPROVAL", createdBy, now, busNo)，命中0行抛"状态已变更"
    // 6. 构造 VO（汇总 totalPrice）
}
```

**为什么提交要加锁**：盘点审批期间库存不能被其它单据改动，加锁保证审批期间账面稳定。快照则留一份「提交时的账面」作审计。

#### 4.2.2 approveApproval —— 审批通过

状态流转 `PENDING_APPROVAL → APPROVED`，核心动作：**平账（账面=实盘）→ 释放锁 → 改状态**。

```java
@Transactional(rollbackFor = Exception.class)
public InventoryOrderApprovalVO approveApproval(ApprovalDTO approvalDTO) {
    // 1. 判空 busNo + approverId
    // 2. 查明细，判空
    // 3. 逐行校验 statusEnum == "PENDING_APPROVAL"
    // 4. 逐明细：查库存 → 校验 totalQuantity 非空(实盘数已录入) → updateQuantity 平账 → releaseLock
    // 5. updateStatusToApproved("APPROVED", approverId, now, busNo)
    // 6. 构造 VO
}
```

**为什么通过要平账**：审批通过即认可盈亏，把库存账面数对齐到实盘数；快照保留作审计。

#### 4.2.3 withdrawApproval —— 撤回

状态流转 `PENDING_APPROVAL → DRAFT`，核心动作：**释放锁 → 删快照 → 改状态**。

```java
@Transactional(rollbackFor = Exception.class)
public InventoryOrderApprovalVO withdrawApproval(OperatorDTO operatorDTO) {
    // 1. 判空 busNo
    // 2. 查明细，判空
    // 3. 逐行校验 "PENDING_APPROVAL"
    // 4. 逐明细：查库存 → releaseLock
    // 5. deleteByBusNo 物理删除快照
    // 6. updateStatusToWithdraw("DRAFT", busNo)  // 清空 applicant_id/apply_time
    // 7. 构造 VO
}
```

**为什么撤回要删快照**：撤回后单据回到草稿，可改完重新提交；而重提会再插一次快照，撞上 `doc_inventory_item_snapshot` 的唯一索引 `(tenant_id, bus_no, inventory_item_id)`。快照索引不含 `is_deleted`，所以软删无效，必须物理删除。

#### 4.2.4 rejectApproval —— 驳回

状态流转 `PENDING_APPROVAL → REJECTED`，核心动作：**释放锁 → 改状态**。

```java
@Transactional(rollbackFor = Exception.class)
public InventoryOrderApprovalVO rejectApproval(ApprovalDTO approvalDTO) {
    // 1. 判空 busNo + approverId
    // 2. 查明细，判空
    // 3. 逐行校验 "PENDING_APPROVAL"
    // 4. 逐明细：查库存 → releaseLock
    // 5. updateStatusToReject("REJECTED", approverId, now, remark, busNo)  // remark落到reason字段
    // 6. 构造 VO
}
```

**为什么驳回不删快照**：驳回是流程终结，快照保留作审计（与审批通过一致）。

### 4.3 Controller 层

四个方法统一加 `@Validated @RequestBody`：

```java
@PutMapping("/submit-approval")
public JsonVO<InventoryOrderApprovalVO> submitApproval(@Validated @RequestBody OperatorDTO operatorDTO) {
    return JsonVO.success(service.submitApproval(operatorDTO));
}
```

## 5. 四个接口的核心动作对比

| 接口 | 状态流转 | 加锁 | 释放锁 | 快照 | 平账 |
|------|----------|------|--------|------|------|
| 提交 submit | DRAFT → PENDING_APPROVAL | ✅ 加锁 | — | ✅ 冻结快照 | — |
| 通过 approve | PENDING_APPROVAL → APPROVED | — | ✅ 释放 | 保留 | ✅ 账面=实盘 |
| 撤回 withdraw | PENDING_APPROVAL → DRAFT | — | ✅ 释放 | ❌ 物理删除 | — |
| 驳回 reject | PENDING_APPROVAL → REJECTED | — | ✅ 释放 | 保留 | — |

## 6. 关键设计决策与踩坑

1. **事务**：四个方法都加 `@Transactional(rollbackFor = Exception.class)`，保证「锁/快照/状态」三者要么全成功要么全回滚。

2. **乐观锁用状态做条件**：`UPDATE ... WHERE status_enum = '当前状态'`。命中 0 行说明状态已被并发改动，抛「单据状态已变更，请刷新后重试」，防止重复提交/重复审批。

3. **加锁幂等**：提交时若发现该库存已被本单据锁过（如驳回后重提），跳过加锁，避免重复锁。

4. **快照唯一索引 → 撤回必须物理删快照**：唯一索引 `(tenant_id, bus_no, inventory_item_id)` 不含 `is_deleted`，软删仍占索引槽位，重提会撞 `DuplicateKeyException`。

5. **`applicant_id` 是 NOT NULL**：提交时 `applicant_id = createdBy`，若 `createdBy` 为 null 会撞数据库非空约束。因此 DTO 上 `@NotNull` + Controller `@Validated` 双重保证。

6. **`@RequestBody` 不能漏**：漏了它，Spring 不从 JSON body 取字段，而改从 URL query 参数/表单绑定，导致 body 里的 `createdBy` 被静默忽略变成 null，最终在数据库层才暴露（这是实测踩过的坑）。
